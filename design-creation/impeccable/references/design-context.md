# Design Context System

Impeccable works best when it can read the same product and design decisions you would give a human designer. Without context, it infers from code alone — usually generic.

## Context Files

| File | Answers | Update when |
|---|---|---|
| `PRODUCT.md` | Platform, users, purpose, positioning, evidence, brand | Strategy changes |
| `DESIGN.md` | Colors, type, components, radii, design rules | Visual system changes |
| `.impeccable/surfaces/*.md` | Per-page strategy, mode, direction | Page strategy changes |
| `.impeccable/design.json` | Machine-readable design metadata | Run `document` to refresh |

**Where Impeccable looks:** Project root first, then `.agents/context/` and `docs/`. In monorepos, each workspace child resolves its own files, falls back to repo root.

## PRODUCT.md

Strategy only — no colors, no fonts, no pixel values.

Contains: Platform (web/ios/android/adaptive), users and their situation, product purpose, positioning, operating context, capabilities, constraints, brand commitments, evidence on hand, design principles, accessibility needs.

**What it should answer:** Who is this for? What does it do? What claim could a neighbor not copy? What real evidence exists?

**What it should NOT contain:** Colors, fonts, visual references, pixel values. Those live in DESIGN.md.

Keeping the two files separate is deliberate: strategy stays stable while the visual system evolves.

## DESIGN.md

Visual system — Google Stitch DESIGN.md format. Six sections in fixed order:
1. Overview (Creative North Star)
2. Colors
3. Typography
4. Elevation
5. Components
6. Do's and Don'ts

Generated by `/impeccable document`. Machine-readable sidecar: `.impeccable/design.json`.

## Four Surface Modes

Each page classified by what the visitor came to do:

| Mode | Pages | Design priority |
|---|---|---|
| **Persuade** | Landing, marketing, campaigns, pricing | Earn attention. Distinctive type, committed palette, image-led |
| **Operate** | App UI, dashboards, editors, admin, tools | Predictable controls, readable states, stable nav, quieter motion |
| **Read** | Docs, guides, help, changelogs | Comprehension first, then reading experience |
| **Experience** | Portfolios, galleries, showcases | Artifact leads, interface recedes |

The mode comes from the **surface**, not from what the company sells. A developer tool's landing page is still Persuade. A fashion house's documentation is still Read.

## Per-Surface Briefs

`.impeccable/surfaces/<page>.md` stores: mode, job, proof sequence, chosen direction. Written by the work itself. Edit when a page's strategy changes.

Scoped requests change output:
```
/impeccable polish the marketing homepage    # Persuade mode
/impeccable audit the billing settings      # Operate mode
```

These get different treatment because they are different jobs.

## Platform Support

`PRODUCT.md` carries a `## Platform` line:

| Value | Meaning |
|---|---|
| `web` | Website or web app (default) |
| `ios` | Native iOS/iPadOS — loads Apple HIG guidance |
| `android` | Native Android — loads Material Design 3 guidance |
| `adaptive` | Flutter/RN/KMP that adapts per OS (alpha) |

Native support is alpha. Live Mode, detector, and hooks all read browser/HTML, so they sit out on native projects. Mobile web stays `web`.

## Keeping Context Fresh

| Change | Run |
|---|---|
| New audience, positioning, purpose, platform, evidence, brand | `/impeccable init` |
| New palette, type, components, radius, design rules | `/impeccable document` |
| Hook says DESIGN.md is newer than design.json | `/impeccable document` |
| One-off intentional detector finding | Add narrow ignore |
| Not sure what's stale | `/impeccable doctor` |

Impeccable checks files at session start, mentions staleness at most once per week per project.

## What Context Enables

With context loaded, Impeccable can:
- Preserve identity instead of "improving" into generic
- Pick right standard for the surface mode
- Replace hardcoded values with documented tokens/components
- Flag drift from DESIGN.md
- Keep Live Mode variants aligned with the system

Context does not replace judgment. Existing code still matters. Intentional exceptions can be documented with detector ignores.

## Init Details

`/impeccable init` scans codebase first (README, package.json, components, tokens, brand assets), forms a hypothesis, then asks at most 3 questions per round:
1. Who the primary user is, in what situation, doing what job
2. What the product makes possible, and what a neighbor could not copy
3. What durable constraints, assets, evidence, or facts future work must preserve

Init deliberately does NOT ask about aesthetics. No colors, no typography, no visual references. Those belong to the design work itself.

If you volunteer a binding visual constraint, init records it without expanding.
